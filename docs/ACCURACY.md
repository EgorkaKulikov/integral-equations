# Точность результата: что библиотека гарантирует, а что нет

Документ отвечает на один вопрос: **насколько можно верить числу, которое вернул
решатель**. Он нужен потому, что успешный возврат из `solve` НЕ означает, что в
ответе есть хоть одна верная значащая цифра, и по одному лишь результату
отличить эти два случая нельзя.

## Почему это отдельный файл

`docs/HPC.md` описывает скорость, `docs/TESTING.md` — гейты, `docs/REFERENCES.md` —
происхождение формул, `docs/baseline-changes.md` — протокол правки эталонов. Ни
один из них не про **границы достижимой точности**: это отдельный предмет, и его
дописывание в конец существующего файла сделало бы предмет того файла нечётким.

## 1. Обратная и прямая ошибка — разные величины

Пусть решается `A x = b`, а численно получен `x`.

| Величина | Определение | Кто её контролирует |
|---|---|---|
| **Обратная** ошибка `ω` | `‖Ax − b‖∞ / max(‖A‖∞‖x‖∞, ‖b‖∞)` | постпроверка внутри `LinearAlgebra.solve` |
| **Прямая** ошибка | `‖x − x*‖∞ / ‖x*‖∞`, где `x*` — истинное решение | НИКТО по умолчанию |

Связь между ними — только через число обусловленности:

```
прямая ошибка  <=  cond∞(A) · ω
```

Плотный решатель библиотеки **обратно устойчив**: измеренная обратная ошибка
составила `3.97e-16`, и она остаётся малой **даже на численно вырожденной
матрице**. Поэтому постпроверка `solve` по построению ловит только откровенный
мусор (нечисловое решение либо невязку масштаба самой системы) — и НИЧЕГО не
говорит о точности.

Прямая же ошибка растёт как `cond(A) · ε`:

| `cond∞(A)` | гарантированно верных десятичных разрядов |
|---|---|
| `~10⁰` | ≈ 16 |
| `2.6e+10` | ≈ 6 |
| `1e+16` и выше | **ни одного** |

### Почему проверка в `solve` сделана по невязке, а не по обусловленности

Это осознанное решение, и менять его нельзя. Задача F1 (уравнение первого рода с
`alpha = 1e-10`) **штатно** даёт `cond ~ 1e10`; отбраковывать её по
обусловленности было бы неверно по сути — это рабочий режим метода, а не
неисправность. Полное обоснование — в KDoc
`LinearAlgebra.SINGULARITY_RELATIVE_TOLERANCE`.

Отсюда следует и устройство диагностики: она **опциональна** и **ничего не
отбраковывает**. Решение, доверять ли числу, принимает вызывающий.

## 2. Как измерить прямую ошибку

```kotlin
val d = LinearAlgebra.solveDiagnosed(a, b)     // решение + диагностика
val x = d.x                                    // побитово то же, что вернул бы solve(a, b)

when (val fe = d.forwardError) {
    is ForwardError.Bounded ->
        println("верных разрядов не меньше ${fe.survivingDigitsOrNull()}")
    is ForwardError.NoFiniteBound ->
        println("конечного cond у матрицы нет вовсе — границы не существует")
    is ForwardError.Unreliable ->
        println("оценка cond недостоверна: невязка обращения ${fe.condition.inversionResidual}")
}
```

Три режима разделены **конструкторами типа**, а не значениями `Double`, и это
принципиально: недостоверную оценку `cond` нельзя случайно распечатать как
результат. `relativeBoundOrNull()` возвращает `null` там, где числа нет.

`NoFiniteBound` и `Unreliable` — **разные** факты. Первый означает, что у матрицы
нет конечного числа обусловленности (`σ_min = 0`); второй — что число, возможно,
конечно, но вычислить его не удалось.

### Чем оценивать `cond`: два пути

| Источник (`ConditionSource`) | Стоимость | Требования | Что различает |
|---|---|---|---|
| `INVERSION` (по умолчанию) | O(n³) | любых нет | на почти вырожденной матрице честно говорит `Unreliable` |
| `SYMMETRIC_SPECTRUM` | O(sweeps · n³) | `A` симметрична | отличает `σ_min = 0` («cond нет») от «cond велико, но конечно» |

Основание для разделения — измерения:

- На **хорошо обусловленной** матрице (система второго рода задачи M1) оценка
  через обращение совпала с независимым методом вращений Якоби на 6–7 значащих
  цифр: `2.252006 / 2.185581 / 2.163922` при `n = 8 / 32 / 128`.
- На матрице дискретизации ядра `1/(1 + t + s)` метод Якоби даёт `σ_min` **ровно
  0**, тогда как оценка через обращение выдавала немонотонный шум порядка
  `1e16…1e19`.
- При `alpha <= 1e-12` невязка обращения `‖A A⁻¹ − I‖∞` достигала `0.08…760` —
  результат обращения не имел смысла.

Диагностика **не встроена** в `solve` и стоит отдельных O(n³) — столько же,
сколько само решение. `solve` вызывается на горячем пути сборки матриц, и
безусловная диагностика удвоила бы его цену (а внутри `Conditioning.inverse` дала
бы ещё и бесконечную рекурсию). Все существующие вызовы `solve` не изменились.

## 3. Граница применимости регуляризованного пути F1 по `alpha`

`FredholmFirstKindSolver` сводит уравнение первого рода к уравнению второго рода
с `c_L = -1/alpha`. Элементы `M` растут как `alpha^{-1}`, `M2` — как `alpha^{-2}`,
поэтому малое `alpha` напрямую ухудшает обусловленность.

### Измеренные последствия

Установлено независимой верификацией (вторым, независимо написанным кодом):

| `alpha` | расхождение между 8 законными вариантами реализации |
|---|---|
| `1e-6` | `0.00 %` |
| `1e-8` | `0.01 %` |
| `1e-10` | **`15.19 %`** |

При `alpha = 1e-10` обусловленность собранной системы составила
`cond_inf ≈ 2.636149e+10`, и восемь законных вариантов реализации (разные порядки
вычисления ядра и правой части, разные решатели плотной СЛАУ) дали **четыре
различных значения** одной и той же величины:
`3.822e-05 / 4.108e-05 / 4.176e-05 / 4.402e-05`.

Априорная оценка `eps · cond / значение ≈ 14.6 %` совпадает с наблюдаемым
разбросом. **Это не ошибка в коде, а ограничение точности.**

Насколько малого изменения достаточно, чтобы сдвинуть ответ: запись точного
решения делением `cos(ωt)/(1+t)` против умножения `cos(ωt) · p`, где `p = 1/(1+t)`,
различается ровно **на одно округление** — и меняет результат на `7.49 %`.

### Практический вывод

**Ниже примерно `alpha = 1e-8` значащих цифр в результате остаётся мало.**
`DEFAULT_REGULARIZATION = 1e-10` попадает **именно в этот диапазон**: значение
воспроизводит экспериментальный выбор авторов цитируемой работы, а не
рекомендацию теории, и требует осознанного принятия. Если задача терпит большее
`alpha`, точность будет выше.

Граница подтверждена и на самой библиотеке
(`FredholmFirstKindConditionTest`): при `alpha = 1e-6` и `1e-8` оценка `cond`
собранной матрицы достоверна, при `alpha = 1e-10` — уже нет.

## 4. Самопроверка без внешнего эталона

Способ, не требующий ни точного решения, ни второй реализации:

> Посчитайте интересующую величину **двумя алгебраически эквивалентными
> способами записи** и сравните.

Например: деление `u/(1+t)` против умножения `u · p` с `p = 1/(1+t)`; или
изменение порядка суммирования. Математически результаты тождественны, различаются
они только округлениями.

**Расхождение — это оценка СНИЗУ для реально доступной точности.** Цифры,
различающиеся между двумя законными записями, не несут информации ни в одной из
них. Сверху точность ограничена величиной `cond_inf · ε`.

Приём именно поэтому и обнаружил эффект: при `alpha = 1e-10` он даёт `15.19 %`, а
при `1e-6` — `0.00 %`.

## 5. Как увидеть `cond` собранной системы

```kotlin
val solver = FredholmFirstKindSolver(basis, funcs, op, rhs, rhsDeriv, alpha = 1e-10)
val est = solver.baseCondition()

println(est.valueOrNull()?.let { "cond_inf = $it" }
    ?: "оценка недостоверна: невязка обращения ${est.inversionResidual}")
```

`baseCondition()` берёт **ту же** матрицу `I − M`, с которой решается система, и
возвращает `ConditionEstimate` — с признаком достоверности, а не голый `Double`.
Метод не вызывается ни одной схемой: его цена O(n⁴) платится только тем, кто явно
спросил.

Это и есть ответ на требование рецензии о протоколе воспроизводимости: число
обусловленности перестало быть внешним наблюдением и стало измеримым из самой
библиотеки.

## Сводка требований

1. Успешный возврат `solve` означает малую **обратную** ошибку — и только её.
2. Прямая ошибка не оценивается, пока её не запросили через `solveDiagnosed`.
3. Большое `cond` **не** является основанием для отбраковки: для F1 это штатный режим.
4. Недостоверная оценка `cond` не может быть напечатана как число — этому мешает тип.
5. При `alpha` ниже примерно `1e-8` результату F1 верить в значащих цифрах нельзя;
   `DEFAULT_REGULARIZATION = 1e-10` лежит ниже этой границы.
