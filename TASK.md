# Задание на разработку: верификация численных методов и устойчивость

## Контекст

Проект решает интегральные уравнения Фредгольма, Вольтерры и Урысона методом
сплайн-коллокации на минимальных сплайнах. К моменту постановки задания выполнено:

* устранены семь дефектов численных методов, каждый закрыт regression-тестом;
* формулы сверены с первичными публикациями, соответствие зафиксировано в
  [`docs/REFERENCES.md`](docs/REFERENCES.md);
* код разделён по назначению: `src/main` (ядро), `src/problems` (модельные задачи),
  `src/demo` (демонстрации, бенчмарк), `src/test`;
* создана сеть характеризационных тестов: 1316 численных значений с относительным
  допуском 1e-9 (`src/test/kotlin/characterization/`);
* состояние НА МОМЕНТ ПОСТАНОВКИ ЗАДАНИЯ: `./gradlew build` — успешно, 206 тестов
  проходят. Актуальные числа см. в разделе «Критерии завершения» и в README.

**Главная нерешённая проблема.** Практически все проверки замкнуты на собственную
реализацию. Характеризационный тест фиксирует, что результат *не изменился*, но не
доказывает, что он *правильный*. Если ошибка была внесена до создания эталона, она
зафиксирована вместе с ним. Настоящей независимой верификации нет.

Задание закрывает этот пробел и устраняет оставшиеся места, где система может дать
неверный результат без диагностики.

### Проблема

Порядок сходимости проверяется лишь в двух местах: `CombinedNystromTest` и
health-check базовой схемы. Для остальных сочетаний «схема × базис × семейство

среагирует на *изменение* значения, но не отличит ухудшение от улучшения, а при
осознанном обновлении эталона деградация будет просто зафиксирована.

Именно отсутствие такой проверки позволило дефекту `kulkarniQuasi` в решателе
Вольтерры (кусочно-линейная реконструкция срезала порядок с ~3.8 до ~1.9)

| Порождающая система | `B`, `H`, `T` |
| Семейство функционалов | `theta`, `xi1`, `mu`, `lambda` (для схем Nyström — только семейства без производных) |

Требования к реализации:

1. Ожидаемый порядок для каждого сочетания задать **явной таблицей** с допуском

### 2.1. Аналитически точные решения (сильнейший эталон) — ЗАКРЫТА

> **СТАТУС: выполнено.** Задачи живут в
> `src/problems/kotlin/problems/analytic/AnalyticProblems.kt` (сепарабельные ядра,
> свёртка через преобразование Лапласа, набор `MANUFACTURED` — MMS),
> проверка — `verification/AnalyticSolutionTest.kt` (7 тестов, тег `slow`, зелёные).

**Вырожденные (сепарабельные) ядра.** Если `K(t,s) = Σ aᵢ(t) bᵢ(s)` — конечная
сумма, уравнение Фредгольма второго рода сводится к **конечной** системе линейных
уравнений, решаемой точно в замкнутой форме, без какой-либо дискретизации.

Пример: `K(t,s) = t·s`, `λ = 1`, `f(t) = t`. Подстановка `u(t) = f(t) + λ·c·t`, где
`c = ∫₀¹ s·u(s) ds`, даёт скалярное уравнение на `c` с точным ответом.

Реализовать не менее трёх задач с сепарабельным ядром (ранг 1, 2 и 3) в
`src/problems/kotlin/problems/analytic/` и проверить, что численное решение сходится
к аналитическому. Это проверяет всю цепочку — базис, функционалы, квадратуру, сборку
матрицы и решение СЛАУ — против результата, полученного **вручную на бумаге**.

**Уравнение Вольтерры с ядром свёртки.** Для `K(t,s) = k(t−s)` уравнение решается
преобразованием Лапласа аналитически. Пример: `K(t,s) = 1`, `λ = 1`, `f(t) = 1` даёт
`u(t) = e^t`. Добавить не менее двух таких задач.

**Метод производных решений (method of manufactured solutions).** Задать желаемое
решение `u*`, подставить в уравнение и вычислить правую часть `f` аналитически (не
квадратурой!). Сейчас `f` строится численным интегрированием, из-за чего ошибка
квадратуры входит и в эталон, и в решение, частично взаимно компенсируясь. Задача с
аналитически выписанной `f` разрывает эту связь.

| Инвариант | Формулировка |
|---|---|
| Линейность | решение для `f₁ + c·f₂` равно сумме решений с тем же коэффициентом |
| Нулевая правая часть | при `f ≡ 0` решение тождественно нулевое |
| Точность на span | если `u*` лежит в span порождающей системы — ошибка машинная |
| Разбиение единицы | `Σ omega_j(t) = 1` в любой точке отрезка |
| Биортогональность | `chi_i(omega_j) = delta_ij` для всех проекторов |
| Идемпотентность | `P(P g) = P g` для семейств с `isProjector = true` |
| Согласованность оператора | `applyNodes` совпадает с `apply` в узлах квадратуры |

Часть инвариантов уже проверяется в `healthchecks` на фиксированных данных — их
следует расширить на случайные входы, а не дублировать.

> плюс `safeDiagonal(t)` — защита в САМОЙ точке деления, срабатывающая при ЛЮБОМ
> вычислении (`solvers/volterra/VolterraSolver.kt`, около строки 764). Покрыто
> regression-тестами `regression/DefectRegressionTest.kt`:
> `defect7_volterraFirstKindRejectsZeroDiagonalBetweenGridPoints` (п. 4 задания) и
> `defect7_volterraFirstKindRejectsTooShortInterval` (п. 3 задания).

### Проблема

`VolterraFirstKindSolver` в `src/main/kotlin/solvers/volterra/VolterraSolver.kt` проверяет
условие `K(t,t) ≠ 0` только в узлах сетки и серединах интервалов
(`KERNEL_DIAGONAL_TOLERANCE`, строка ~561). Фактически деление на `K(t,t)`
происходит:

* в `gEff` — во **всех** гауссовых узлах квадратуры;
* внутри `deriv4` — в точках `t ± k·FINITE_DIFFERENCE_STEP`, которые не совпадают
  ни с узлами, ни с серединами.

Ядро, обращающееся в ноль между проверенными точками, даст `NaN` или `Inf` без
диагностики: пользователь получит бессмысленный результат, не узнав об этом.

### Что сделать

1. Расширить проверку на точки, где деление реально выполняется: гауссовы узлы
   составной квадратуры и шаблон конечной разности.
2. Добавить защиту в самих точках деления: при обнаружении значения ниже порога —
   исключение с указанием точки `t` и величины `K(t,t)`, а не молчаливый `NaN`.
3. Проверить, не выходит ли шаблон `t ± 4·FINITE_DIFFERENCE_STEP` за пределы
   отрезка при малой его длине (`b − a` порядка `1e-3`). Константа абсолютная; если
   выход возможен — сделать шаг относительным к длине отрезка либо явно запретить
   такие отрезки с внятным сообщением.
4. Regression-тест: ядро, положительное в узлах и серединах, но обращающееся в ноль
   между ними, обязано вызывать исключение, а не возвращать `NaN`.

## Задача 4. Единая диагностика расходимости — ЗАКРЫТА

> **СТАТУС: выполнено.** Выбран вариант с полями в `numerics/SolutionFunc.kt`:

> `throwOnDivergence = false`. Проверка — `convergence/DivergenceContractTest.kt`.
> Численная нейтральность соблюдена: эталон `baseline-eh.tsv` не обновлялся.

### Проблема

Итерационные методы ведут себя по-разному при недостижении сходимости:

| Метод | Поведение сейчас |
|---|---|
| `combinedNystrom` (оба решателя) | бросает `IllegalStateException` — **правильно** |
| `kulkarniQuasi` (Фредгольм, строка ~252) | молча возвращает последний итерант |
| `kulkarniQuasi` (Вольтерра) | молча возвращает последний итерант |
| Ньютон в решателе Урысона | записывает предупреждение в лог и возвращает результат |
| Гаусс–Ньютон (Урысон, первый род) | записывает предупреждение в лог |

Пользователь библиотеки не может отличить сошедшийся результат от расходящегося:
предупреждение в логе при программном использовании не будет замечено.

### Что сделать

Привести к единому, явному контракту:

1. Ввести признак сходимости в возвращаемом значении. Решение о форме — за
   исполнителем; допустимые варианты: поле `converged: Boolean` и `iterations` в
   `SolutionFunc`, либо отдельный тип результата. Выбранный вариант обосновать.
2. Поведение по умолчанию — исключение при недостижении сходимости (как в
   `combinedNystrom`): молчаливый возврат неверного результата недопустим.
3. Предусмотреть режим, позволяющий получить неcошедшийся результат осознанно
   (например, параметр `throwOnDivergence: Boolean = true`) — это нужно для
   исследовательских сценариев и для тестов.
4. Логирование сохранить как дополнение, а не как единственный канал сигнала.
5. Тесты: задача, заведомо не дающая сходимости за отведённое число итераций,
   должна приводить к исключению; при отключённом режиме — к результату с
   `converged = false`.

**Внимание к совместимости.** Изменение публичного API затрагивает `src/demo`,
`src/problems` и тесты. Численные результаты меняться **не должны**:
`characterization.EhCharacterizationTest` обязан проходить без обновления эталона.
