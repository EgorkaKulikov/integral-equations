# Numerical-Algorithms

Библиотека численного решения линейных и нелинейных интегральных уравнений методом
сплайн-коллокации на **минимальных сплайнах**.

![JVM](https://img.shields.io/badge/JVM-21-orange?logo=openjdk&logoColor=white)
![Gradle](https://img.shields.io/badge/Gradle-8.9-02303A?logo=gradle&logoColor=white)
![License](https://img.shields.io/badge/license-Apache%202.0-blue.svg)

## Какие задачи решает

Библиотека находит приближённое решение интегральных уравнений трёх классов:

| Класс | Уравнение | Особенность |
|-------|-----------|-------------|
| **Фредгольм** | u(t) − λ∫ₐᵇ K(t,s) u(s) ds = f(t) | линейное, постоянные пределы |
| **Вольтерра** | u(t) − λ∫ₐᵗ K(t,s) u(s) ds = f(t) | линейное, переменный верхний предел |
| **Урысон** | u(t) − ∫ₐᵇ K(t,s,u(s)) ds = f(t) | нелинейное |

Поддерживаются уравнения **первого и второго рода**. Уравнения первого рода
некорректны по Адамару и решаются с регуляризацией.

## Основные возможности

* Три порождающие системы минимальных сплайнов: полиномиальная `B`, гиперболическая
  `H`, тригонометрическая `T`.
* Пять классов аппроксимационных функционалов, дающих восемь именованных вариантов:
  проекционные `theta`, де Бура–Фикса `xi⁰`, `xi¹`, `xi²`, усредняющие `mu`,
  трёхточечные `lambda`, а также дискретизованные `xitilde¹`, `xitilde²` (не требуют
  вычисления производных; вариант `xitilde⁰` не реализован по построению).
* Схемы решения для линейных уравнений: базовая коллокация, итерация Слоана, схема
  Кулкарни и её итерированный вариант, классический и комбинированный методы Nyström —
  каждый также в итерированном варианте. Для уравнения Урысона итерированных
  вариантов Nyström нет.
* Регуляризация уравнений первого рода: метод Wazwaz (Фредгольм), сведение
  дифференцированием (Вольтерра), регуляризация Тихонова с выбором параметра по
  принципу невязки Морозова (Урысон).
* Сетки: равномерная, квазиравномерная, геометрическая, градуированная.
* Подключаемый бэкенд линейной алгебры с автоматическим откатом на чистый JVM.
* Явный контекст вычислений `NumericsContext` (бэкенд + параллельная сборка) вместо
  глобального изменяемого состояния. Несовпадение контекста решателя и его
  зависимостей отвергается с диагностикой, а не сдвигает молча младшие биты.
* Единый контракт сходимости: итерационные схемы не могут молча вернуть
  несошедшийся результат (см. «Входные и выходные данные»).
* **Независимая верификация**: сверка со SciPy/NumPy, аналитически точные решения и
  сверка с опубликованными значениями. Сверка со SciPy (`scipyVerify`) требует venv
  с Python и вынесена в отдельную задачу и job CI; остальное входит в `./gradlew check`
  — см. «Запуск тестов».

## Поддерживаемые численные методы и их источники

Каждый метод сопровождается ссылкой на первичную публикацию. Полная таблица

Кратко об основных источниках: минимальные сплайны — Демьянович (1994) и Makarov
(2012); функционалы де Бура–Фикса — Kulikov, Makarov (2019); проекционные
функционалы — Kulikov, Makarov (2025); итерация Слоана — Sloan (1976); схема
Кулкарни — Kulkarni (2003); метод Nyström — Allouch и др. (2021), Remogna и др.

Engl, Hanke, Neubauer (1996).

**Что не имеет опубликованного источника** (помечено в коде и в
`docs/REFERENCES.md`): дискретизованные функционалы `xitilde`, краевые функционалы
`xi`, схема Кулкарни для квазиинтерполянтов, комбинированный Nyström для уравнения
Вольтерры.

## Ограничения и область применимости

* **Размер задачи.** Матрицы плотные, решение СЛАУ имеет сложность O(N³) при
  N = n + 2. Практический предел на настольной машине — порядка N ~ 10³.
* **Гладкость данных.** Порядки сходимости достигаются при достаточно гладких ядре
  и правой части. Для ядер со слабой особенностью гарантии не переносятся.
* **Теоремы о порядках** доказаны для уравнения Фредгольма с равномерной сеткой и
  полиномиальными B-сплайнами. Для уравнения Вольтерры аналогов в известной
  литературе нет; наблюдаемые порядки следует трактовать как численный результат.
* **Комбинированный Nyström** даёт выигрыш для уравнения Фредгольма (порядок около
  7 против 4 у классического). Для уравнения Вольтерры выигрыша **не обнаружено**.
* **Уравнения первого рода** некорректны: точность ограничена уровнем шума данных и
  выбором параметра регуляризации.
* Семейства `xi` требуют производных образа и потому несовместимы со схемой Nyström;
  для этого случая предназначены функционалы `xitilde`.

## Требования к окружению

Для использования библиотеки:

* JDK 21 или новее;
* Gradle не требуется — используется wrapper.

Для обычного прогона тестов ничего больше не требуется. **Python 3** нужен только
для внешней сверки со SciPy/NumPy — задачи `./gradlew scipyVerify`. Окружение
готовится автоматически: задача `setupScipyVerification` создаёт виртуальное
окружение `.venv-verify` и ставит версии из `tools/requirements-verify.txt`
(при первом запуске требуется доступ в сеть); дальше она отмечается как
`UP-TO-DATE`. Каталог `.venv-verify` (порядка 200 МБ) в репозиторий не попадает.

Поведение при отсутствии окружения различается по задачам намеренно: `./gradlew test`
сообщает о пропуске сверки, а `./gradlew scipyVerify` выставляет `scipy.required=true`
и при неработоспособном окружении **падает**. Иначе job `scipy` в CI мог бы стать
зелёным, ничего не проверив.

Нативный BLAS (OpenBLAS через multik) подключается автоматически. Если библиотека
недоступна, происходит откат на реализацию на чистом JVM; корректность результатов
при этом сохраняется, снижается только скорость.

## Пример использования

Решение уравнения Фредгольма второго рода и оценка погрешности. Для модельных задач
из каталога `problems` правая часть и её производные берутся из самой задачи, поэтому
решатель собирается одним вызовом `secondKindSolver`:

```kotlin
import numerics.GaussLegendre
import numerics.GeneratingSystem
import numerics.Grid
import numerics.MinimalSplineBasis
import numerics.functionals.ProjFunctionals
import numerics.functionals.errorEh
import problems.fredholm.FredholmProblem
import problems.fredholm.secondKindSolver
import solvers.fredholm.FredholmOperator

fun main() {
    val problem = FredholmProblem.F2          // K(t,s) = 1/(1+t+s), u*(t) = 1/(t+1)
    val grid = Grid.uniform(n = 64)
    val basis = MinimalSplineBasis(GeneratingSystem.B, grid)
    val funcs = ProjFunctionals(basis)
    val op = FredholmOperator(problem.kernel, grid, GaussLegendre(8))

    val solver = secondKindSolver(problem, basis, funcs, op)

    val approximate = solver.base()           // базовая схема коллокации
    val refined = solver.combinedNystrom()    // схема более высокого порядка

    println("E_h (базовая)         = ${errorEh({ t -> problem.exact(t) }, approximate.eval, grid)}")
    println("E_h (комбин. Nyström) = ${errorEh({ t -> problem.exact(t) }, refined.eval, grid)}")
}
```

Для собственной задачи ядро и правая часть задаются напрямую — `FredholmSecondKindSolver`
принимает `cL`, `rhs = RhsWithDerivatives(value, deriv, deriv2)` и, при необходимости,
`NumericsContext`.

## Входные и выходные данные

**Вход.** Ядро уравнения и, при использовании функционалов, требующих производных, —
его частные производные:

| Уравнение | Тип ядра | Требуемые производные |
|---|---|---|
| Фредгольм | `KernelF` | `K_t`, `K_tt` |
| Вольтерра | `KernelV` | `K_t`, `K_tt` и дополнительно `K_s` (нужна из-за диагонали `K(t,t)`) |
| Урысон | `solvers.uryson.Kernel` | `∂K/∂u` — для матрицы Якоби схем Ньютона и Гаусса–Ньютона |

Кроме ядра задаются правая часть `f(t)` и её производные, сетка, порождающая система и
семейство функционалов.

> Важно: если семейство функционалов использует вторые производные (`xi⁰`), а
> производные ядра оставлены нулевыми, результат будет неверным. Такое несоответствие
> выявляется тестами, а недоступные пути явно отвергаются с диагностикой.

**Выход.** Единый для всех трёх решателей объект `numerics.SolutionFunc`:

| Поле | Смысл |
|---|---|
| `eval: (Double) -> Double` | приближённое решение, вычислимое в любой точке отрезка |
| `converged: Boolean` | достигнута ли сходимость; для прямых схем тривиально `true` |
| `iterations: Int` | число выполненных итераций (`0` для прямых схем) |
| `residual: Double` | достигнутая величина критерия останова |

Для регуляризованного уравнения Урысона первого рода возвращается
`solvers.uryson.FirstKindSolution` с полями `coeffs`, `eval`, `alpha` (выбранный
параметр регуляризации), `resid` (невязка) и `omega` (значение стабилизатора).

### Контракт сходимости

Итерационные схемы (Кулкарни для квазиинтерполянтов, комбинированный Nyström, Ньютон
в задачах Урысона) **не могут молча вернуть несошедшийся результат**: по умолчанию
бросается `IllegalStateException` с указанием числа итераций, достигнутой и требуемой
точности. Предупреждение в журнал остаётся дополнительным каналом, а не единственным
сигналом: при программном использовании библиотеки запись в лог осталась бы
незамеченной.

Исключение — `UrysonFirstKindSolver` (схема Гаусса–Ньютона), где `throwOnDivergence`
по умолчанию `false`: гомотопия по параметру регуляризации вызывает решение при
фиксированном `alpha` десятки раз, и недостижение шагового критерия на промежуточных
значениях — штатная часть пути, а не отказ.

Для исследовательских сценариев предусмотрен осознанный доступ к несошедшемуся
результату — параметр решателя `throwOnDivergence = false`:

```kotlin
val solver = FredholmSecondKindSolver(/* ... */, throwOnDivergence = false)
val solution = solver.combinedNystrom()
if (!solution.converged) {
    println("не сошлось за ${solution.iterations} итераций, невязка ${solution.residual}")
}
```

Схема `kulkarni()` итерационна только для квазиинтерполянтов (`mu`, `lambda`): для
проекторов (`theta`, `xi`) это прямая схема, и `converged` у неё всегда `true`.

## Запуск тестов

Тесты разделены по времени выполнения тегами JUnit (`fast`, `slow`, `scipy`), на
каждый тег есть своя задача. Причина разделения: проверка после правки
должна занимать секунды, иначе её перестают делать.

```bash
./gradlew fastTest                 # быстрый набор: 289 тестов, единицы секунд
./gradlew slowTest                 # прогон по крупным сеткам: 23 теста, ~8.5 мин
./gradlew scipyVerify              # внешняя сверка со SciPy/NumPy: 9 тестов, 60 проверок
./gradlew characterizationTest     # гейт численной нейтральности: 5 тестов, ~27 с
./gradlew extraCharacterizationTest # гейт combinedNystrom и неравномерных сеток, ~19 с
./gradlew convergenceOrderTest     # полная матрица порядков сходимости: 168 сочетаний, 1.5-2 мин
./gradlew test                     # весь набор сразу — СМ. ПРЕДУПРЕЖДЕНИЕ НИЖЕ
./gradlew test --tests 'healthchecks.*'       # произвольная выборка по имени
./gradlew koverHtmlReport          # отчёт о покрытии
```

**Состав `./gradlew check`** (проверено `check --dry-run`): `fastTest`,
`characterizationTest`, `extraCharacterizationTest`, `slowTest` — объявлены явно в
`build.gradle.kts` — плюс `koverVerify` от плагина покрытия. Полный прогон занимает
около 9 минут, из которых `slowTest` — 8 мин 39 с.

**Почему `test` НЕ входит в `check`, а `slowTest` входит.** `test` дублирует
`fastTest` и `slowTest` вместе — самые дорогие классы гонялись бы дважды, а состав
гейта стал бы неявным. `slowTest` содержит единственную сверку с внешним источником
правды (`PublishedValuesTest`, 708 опубликованных чисел): набор, который нигде не
запускается, — не гейт, а декорация. Включён он **явным `dependsOn("slowTest")`**;
вариант «сделать его источником покрытия Kover» проверен и отвергнут — `check
--rerun-tasks` падает по памяти (`exit value 137`, SIGKILL), поскольку инструментация
Kover поверх матриц до n = 64 не укладывается в память. Цена выбора: строки,
покрытые только slow-классами, не попадают в отчёт покрытия — но сами проверки
исполняются.

Для быстрого цикла правка-проверка используйте `fastTest` (единицы секунд) либо
`fastTest characterizationTest extraCharacterizationTest` (~1 мин).

Об одной ловушке при добавлении новых задач типа `Test`: Kover делает источником
покрытия ЛЮБУЮ такую задачу, не перечисленную в `disabledForTestTasks`, а вместе с этим —
зависимостью `koverVerify`, который уже в `check`. Именно так `convergenceOrderTest`
одно время молча попал в `check` и раздул его, не добавив ни одной покрытой строки
сверх быстрого поднабора того же класса; сейчас он из источников покрытия исключён.

| Задача | Состав | В `check` |
|---|---|---|
| `fastTest` | всё, кроме перечисленного ниже: ядро, решатели, инварианты, regression, быстрый поднабор порядков сходимости | да |
| `characterizationTest` | `EhCharacterizationTest` против `baseline-eh.tsv` | да |
| `extraCharacterizationTest` | `ExtraCharacterizationTest` против `baseline-extra.tsv` (`combinedNystrom`, неравномерные сетки) | да |
| `slowTest` | `PublishedValuesTest`, `EhCharacterizationTest`, `ExtraCharacterizationTest`, `CrossSchemeConsistencyTest`, `AnalyticSolutionTest`, `ConvergenceOrderTest` — прогон по сеткам до n = 64 | да (явный `dependsOn`) |
| `convergenceOrderTest` | полная матрица `ConvergenceOrderTest`, 168 сочетаний, 1.5-2 мин | нет, но гоняется в CI (job `characterization`) и входит в `slowTest` |
| `scipyVerify` | `ScipyCrossVerificationTest` — быстрый, но требует venv с Python | нет (job `scipy` в CI) |

Категории тестов по назначению (ортогонально тегам по времени):

| Категория | Назначение |
|---|---|
| `numerics.*` | модульные тесты ядра: сетки, квадратура, сплайны, линейная алгебра |
| `verification.*` | **независимая верификация**: сверка со SciPy/NumPy, аналитически точные решения, опубликованные значения, перекрёстная согласованность схем |
| `convergence.*` | контракт сходимости и эмпирические порядки сходимости |
| `healthchecks.*` | математические инварианты: биортогональность, разбиение единицы, точность на span |
| `characterization.*` | фиксация численных результатов (1366 значений, допуск 1e-9) |
| `regression.*` | воспроизведение ранее обнаруженных дефектов |
| `solvers.*` | поведение решателей |

### Выбор бэкенда линейной алгебры в тестах

Все тестовые задачи получают системное свойство `numerics.backend` (по умолчанию
`multik`). Это существенно: эталон `baseline-eh.tsv` снят на multik/OpenBLAS и
**привязан к нему** — прогон `-Dnumerics.backend=reference` даёт 4/4 падения
`EhCharacterizationTest` с расхождением до 5.7e-2 при допуске 1e-9. Причина
закономерна: уравнение первого рода F1 плохо обусловлено, и разные реализации LU
на нём расходятся. Внешнее значение свойства уважается и перекрывает умолчание,
поэтому прогон на обоих бэкендах возможен явно.

Служебные задачи, не входящие в обычный прогон:

| Задача | Назначение |
|---|---|
| `captureBaseline` | переснять эталонный снимок `E_h` в `build/baseline/` (источник `baseline-eh.tsv`) |
| `captureExtraBaseline` | переснять дополнительный снимок `build/baseline/baseline-extra.tsv` (`combinedNystrom`, неравномерные сетки, отрезок `[0,2]`) |
| `dumpVerificationArtifacts` | выгрузить внутренние артефакты для ручного разбора расхождения |
| `setupScipyVerification` | подготовить окружение Python со SciPy (вызывается автоматически из `scipyVerify`) |

Задачи `captureBaseline` и `captureExtraBaseline` следует запускать осознанно — только
когда изменение алгоритма обосновано, с фиксацией старых и новых значений
(см. [`docs/baseline-changes.md`](docs/baseline-changes.md)).

## Непрерывная интеграция

Конфигурация — [`.github/workflows/ci.yml`](.github/workflows/ci.yml). Запуск: push в любую
ветку, pull request и ежедневно в 03:00 UTC. Разделение на job'ы повторяет разделение
тестов по тегам: обратная связь на PR обязана быть быстрой.

| Job | Что гоняет |
|---|---|
| `fast` | `fastTest --tests numerics.backend.BackendSpiTest` (диагностика бэкенда), затем `fastTest koverXmlReport compileDemoKotlin compileProblemsKotlin` |
| `characterization` | `characterizationTest` — гейт численной нейтральности, затем `convergenceOrderTest` — полная матрица порядков сходимости |
| `scipy` | `scipyVerify` с кэшированным `.venv-verify` |
| `full` | `slowTest` — 23 теста, включая единственную сверку с опубликованными таблицами (`timeout-minutes: 45`) |

Три детали, важные при правках CI. Первая: job `fast` начинается с отдельного
прогона `BackendSpiTest` — без него молчаливый откат с multik на `ReferenceBackend`
выглядел бы как «рефакторинг испортил числа». Вторая: `full` НЕ включен с
`continue-on-error: true` — зелёная галочка при невыполненных проверках хуже
отсутствующего job'а. Третья: у `full` НЕТ условия `if:` на ветку `main` — гейт,
работающий только после мержа, сообщает о поломке слишком поздно.

## Независимая верификация численных методов

Характеризационные тесты фиксируют, что результат *не изменился*, но не доказывают,
что он *правильный*: ошибка, внесённая до создания эталона, была бы зафиксирована
вместе с ним. Поэтому методы проверяются средствами, НЕ зависящими от кода проекта.

| Средство | Что даёт |
|---|---|
| Аналитически точные решения | сепарабельные ядра (ранг 1–3), свёртка через преобразование Лапласа, метод производных решений — всё выведено вручную, без квадратуры проекта |
| Опубликованные значения | 708 ключей (422 `E_h` + 286 `p_h`) из 18 таблиц статьи, фактически сверяется 655 = 260 (F2/F2exp) + 42 (F1) + 341 (V2/V2exp/V2win) + 12 (V1); из остальных 53 ключей 29 отсечены порогом машинного шума (`NOISE_FLOOR = 1e-13`, применяется и к опубликованным `E_h`, и к обеим погрешностям пары при сверке `p_h`), а 24 `p_h` уравнения F1 неприменимы (там сверяются только `E_h`); допуск 2 % |
| Сверка со SciPy/NumPy | послойная сверка внутренних величин со сторонними библиотеками |
| Перекрёстная проверка схем | разные схемы обязаны сходиться к одному пределу |
| Порядки сходимости | `ConvergenceOrderTest`: эмпирический порядок против явной таблицы ожиданий |
| Математические инварианты | биортогональность, разбиение единицы, идемпотентность проекторов |

Всё перечисленное автоматизировано; в `./gradlew check` не входит только сверка со
SciPy — она требует venv с Python (задача `scipyVerify`, job `scipy` в CI).

Общий допуск сверки с публикацией — 2 %. Для шести ключей таблицы `table-f1.tex`
действует узкий класс 8 %, выведенный из измеренного разброса между реализациями LU
на этих же ключах (7.267 %) — уравнение первого рода F1 плохо обусловлено
(`cond(I - M) ~ 1e10`). Потеря строгости скомпенсирована расширенным покрытием F1 в
`baseline-eh.tsv` (54 ключа, допуск 1e-9); границы послабления зафиксированы
константой и проверяются отдельным быстрым тестом.

### Слои сверки со SciPy

Сверка идёт снизу вверх — так при расхождении сразу видно, какой слой виноват, а не
только факт несовпадения итоговых чисел. Реализация:
`verification.ScipyCrossVerificationTest` и
[`tools/verify_with_scipy.py`](tools/verify_with_scipy.py).

| Слой | Проверяемое | Эталон |
|---|---|---|
| L1 | узлы и веса квадратуры Гаусса–Лежандра | `numpy leggauss` |
| L2 | решение СЛАУ `(I - M) c = g` | `scipy.linalg.solve` |
| L3 | базис минимальных сплайнов и две производные | `scipy.interpolate.BSpline` |
| L4/L5 | образы операторов и правые части | `scipy.integrate.quad` |
| L6a | эталонный Nyström против точного решения | независимый метод Nyström на 80 узлах |
| L6b | `E_h` схем `base`/`sloan` проекта и их порядки сходимости | тот же эталонный Nyström |

Сверка L3 возможна только для полиномиальной системы `B`: узлы кратности 3 на концах
задают клампованный вектор узлов степени 2. Гиперболические и тригонометрические
минимальные сплайны, а также семейства аппроксимационных функционалов аналогов в
сторонних библиотеках не имеют — для них внешняя сверка неприменима принципиально, и
проверка опирается на математические инварианты. Подробности — в
[`docs/REFERENCES.md`](docs/REFERENCES.md), раздел 6.

## Производительность

Все приведённые числа получены командой `./gradlew runBenchmark` на конкретной
конфигурации и воспроизводимы на ней. Бенчмарк печатает параметры окружения при
каждом запуске.

**Условия измерения.** Apple Silicon (aarch64), 8 ядер; macOS 15.5;
OpenJDK 21.0.10; бэкенд multik-cpu (OpenBLAS); 7 повторов после 3 прогревочных;
агрегация — медиана.

### Масштабирование по размеру задачи

Полное решение уравнения Фредгольма (задача F2, базис B): построение решателя,
сборка матрицы и решение СЛАУ.

| n | dim | медиана, мс | мин, мс | макс, мс | разброс, % |
|---|-----|-------------|---------|----------|------------|
| 16 | 18 | 1.58 | 1.09 | 2.20 | 69.8 |
| 32 | 34 | 2.09 | 1.57 | 5.05 | 166.6 |
| 64 | 66 | 4.27 | 3.44 | 6.09 | 62.0 |
| 128 | 130 | 20.66 | 17.99 | 28.39 | 50.4 |
| 256 | 258 | 131.36 | 118.49 | 152.43 | 25.8 |

### Масштабируемость по числу потоков

Сборка матрицы при n = 256. Число потоков задаётся явно выделенным пулом.

| потоков | медиана, мс | ускорение | эффективность | последовательная доля |
|---------|-------------|-----------|---------------|----------------------|
| 1 (последовательно) | 677.02 | 1.00 | 1.00 | — |
| 2 | 338.04 | 2.00 | 1.00 | −0.001 |
| 4 | 173.20 | 3.91 | 0.98 | 0.008 |
| 8 | 117.00 | 5.79 | 0.72 | 0.055 |

Эффективность снижается с ростом числа потоков, а оценка последовательной доли по
формуле Карпа–Флэтта растёт, что указывает на накладные расходы распараллеливания,
а не на неустранимую последовательную часть.

**Ограничения измерений.** Разброс для малых задач превышает 100 %, поэтому
соответствующие значения ориентировочны: на таких временах доминируют JIT и тепловой
режим CPU, а не сам алгоритм. Показателен только правый край таблицы — повторный
прогон дал для n = 256 те же 131.9 мс (расхождение 0.4 %), тогда как масштабируемость
по потокам между прогонами колебалась заметно (ускорение на 8 потоках 5.79 против
4.60). Измерения выполнены на одной машине и одной конфигурации JVM; перенос выводов
на другое оборудование требует повторного запуска. Ускорение измерено только для
сборки матрицы: решение СЛАУ использует внутреннюю многопоточность нативного BLAS,
которая в этом эксперименте не разделяется. Максимальное исследованное число потоков
равно числу физических ядер; поведение при большем числе потоков не проверялось.

Бенчмарк печатает также сравнение бэкендов линейной алгебры (multik против
reference) по отдельным операциям; эти числа в документации не фиксируются из-за
высокой чувствительности к фоновой нагрузке машины.

## Известные ограничения

* Комбинированный Nyström для уравнения Вольтерры реализован по аналогии с
  уравнением Фредгольма, но теоретического обоснования не имеет и выигрыша по
  точности не даёт.
* Схема Кулкарни для квазиинтерполянтов (`mu`, `lambda`) не имеет доказательства
  сходимости: теория требует свойства проектора. Реализована простой итерацией и
  требует сжатия (спектральный радиус меньше единицы); при нарушении этого
  условия схема бросает исключение, а не возвращает неверный результат.
* Сверка со SciPy покрывает только полиномиальную систему `B`: для `H`, `T` и
  семейств функционалов аналогов в сторонних библиотеках нет, и проверка
  опирается на математические инварианты.
* Порядки сходимости сочетаний «схема × базис × семейство» проверяются
  `convergence.ConvergenceOrderTest` — 168 сочетаний в полной матрице (задача
  `convergenceOrderTest`, 1.5-2 мин). Покрытие всё же не сплошное: 24 сочетания
  `xi1` со схемами Nyström исключены по сути дела — `nystromSupport()` запрещает
  семейства, требующие производных образа; в быстрый поднабор входят 32 сочетания
  плюс 64 проверки span-задач.
* Значение параметра регуляризации α = 1e-10 для уравнения Фредгольма первого рода
  взято из работы Kulikov, Makarov (2023) как экспериментальный выбор; теоретического
  обоснования именно этой величины нет.

## Правила участия в разработке

1. Перед изменением численного алгоритма зафиксируйте текущее поведение:
   `./gradlew captureBaseline`.
2. Изменения не должны нарушать `characterization.*`. Если изменение обосновано
   (исправление ошибки), обновите эталон осознанно и укажите в описании коммита
   старые и новые значения — подгонять допуски нельзя.
3. Каждое исправление ошибки сопровождайте regression-тестом, который падает на коде
   до исправления.
4. Новый метод сопровождайте ссылкой на первичную публикацию в
   `docs/REFERENCES.md`. Если источника нет, пометьте это явно.
5. Комментарии и документация — на русском языке.
6. Перед отправкой изменений: `./gradlew build` должен завершаться успешно
   (около 9 минут; в цикле разработки достаточно `./gradlew fastTest`).
